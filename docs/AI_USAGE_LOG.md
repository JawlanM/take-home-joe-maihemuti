# AI Usage Log

I used an AI coding assistant for parts of the implementation and reviewed its output by reading the code, running mypy and Ruff, and using the app in the browser. These are six specific moments where I corrected or rejected its suggestions.

| # | What the AI suggested | What I changed | Why |
|---|---|---|---|
| 1 | **Edit endpoint:** read the candidate, write the update, and return the write result without checking it. | Used the same “update or 404” helper as the other writes. | A candidate could be deleted between the read and the write, leaving the update with no result and causing a 500. mypy flagged the possible `None` return. A missing candidate should produce a consistent 404. |
| 2 | **AI module:** documented as “never raises,” but created the Gemini client outside the `try`/`except`. | Moved client creation inside the error handling and added a test for client-initialisation failure. | Invalid configuration or a client-initialisation error could escape instead of returning a failed summary. The implementation needed to match the module’s promise that an AI failure would not prevent saving a candidate. |
| 3 | **Partial updates:** silently ignored explicit `null` values for required fields such as `name`. | Rejected explicit `null` for required fields with a 422, while still allowing `null` to clear optional phone and source fields. Added tests. | Omitting a field means “keep its current value”; explicitly sending `null` is a different request. Silently ignoring it hides client mistakes and makes the API harder to understand. |
| 4 | **List endpoint:** used five separate filter and sort parameters, with `Depends(get_service)` repeated across the routes. | Grouped the query parameters into a `ListQuery` model and defined the shared dependency as `ServiceDep`. | Keeping related query options together makes validation and future changes easier to follow. The shared dependency alias also removes repetition without adding another architectural layer. |
| 5 | **Archived view:** a “Show archived” checkbox mixed archived candidates into the active list. With no archived candidates, selecting it produced no visible change. | Replaced it with Active / Archived / All views, a specific “No archived candidates” empty state, and a way back to the active view. Kept the previous results visible while filters refresh. | The original interaction looked unresponsive and offered no way to view only archived candidates. The revised control makes the selected view and its result clearer. |
| 6 | **Avatar initials:** used the first character of the first two words in a name. | Ignored nicknames in brackets or quotes, counted letters only, used the first and last name, and added a “?” fallback. Checked 11 names, including accented, hyphenated, and Chinese names. | My name, “Maihemuti (Joe) Jiewulan,” produced “M(”. Trying a real name exposed an assumption that the sample names did not catch. |

I also revised smaller UI choices after using the app: a back link that was easy to miss, an unclear “Load .txt file” label, and stage colours that were difficult to distinguish. I replaced native dropdowns to match the visual design and included keyboard controls and ARIA attributes in the custom component; those implementation details alone do not establish full accessibility.
